# Arquitectura modular de escenarios

Objetivo: convertir la creación y ejecución de escenarios en un flujo modular, versionado y verificable, manteniendo el dominio de ciberseguridad y preparando una futura autoría administrativa sin implementar todavía esa interfaz.
Rama: `feat/quality-improve`. Estrategia de entrega: `single-pr` sobre la rama actual, por decisión del usuario. Runner: Vitest, pruebas backend existentes, Biome, TypeScript y builds pnpm.
Previsión: más de 400 líneas autoradas. La canalización comparte contrato, lockfile, frontend, backend y migración, por lo que se conserva como una unidad funcional coherente; la documentación se entrega en un segundo commit. Esta excepción evita estados intermedios que no pueden instalarse o reproducirse con el lockfile.

## Specs

- **S1 — Modularidad.** Requisito del usuario: «quiero que para todos los puntos que haz dicho y me haz recomendado lo implementes y refactorices lo que hay actualmente». La arquitectura debe separar catálogo, manifiesto versionado, entorno reutilizable, reglas/evaluación, compilación al ECS y persistencia de revisiones, conservando compatibilidad funcional con los escenarios actuales.
- **S2 — Extensión segura.** Un ejercicio nuevo que use capacidades existentes debe poder añadirse declarativamente y pasar validación estructural, referencial, semántica, compilación y smoke test determinista. Una capacidad nueva de ciberseguridad seguirá requiriendo código y pruebas. Los activos y capacidades se referencian por identificadores confiables; no se admite contenido ejecutable arbitrario.
- **S3 — Fuente canónica.** Eliminar registros duplicados de escenarios y títulos. El catálogo publicado debe ser la fuente única para selección, carga y metadatos; los escenarios generados deben atravesar el mismo contrato, validación y compilador que los incorporados al repositorio.
- **S4 — Versionado y reproducibilidad.** Cada manifiesto debe declarar versión de esquema y revisión; una ejecución persistida debe poder vincularse a una revisión inmutable. Registrar hash de contenido, versión del motor, semilla y versión de activos cuando correspondan, preservando los datos existentes mediante una migración compatible.
- **S5 — Preparación para autoría futura.** Modelar el ciclo `draft → validated → published → archived` y la persistencia necesaria para que un administrador futuro pueda editar y publicar manifiestos, sin construir ahora la interfaz administrativa.
- **S6 — Documentación progresiva.** Requisito del usuario: «sí o sí haya como un documento resumen que trate de ser autocontenido y se entienda de manera simple, ya si el dev quiere ahondar, entonces ahí si se conecta con los otros archivos». Crear un resumen autocontenido con Mermaid, documentos técnicos enlazados y un ADR para la decisión híbrida.
- **S7 — Guía de creación.** Requisito del usuario: «un documento guía en guides, para que el desarrollador sepa cómo crear un nuevo escenario» y «el desarrollador tendría una ruta clave como para hacer los escenarios». La guía debe ofrecer un camino feliz, plantilla, comandos de validación, criterios de éxito y ruta alternativa cuando haga falta una capacidad nueva.
- **S8 — Alcance documental.** Omitir de todos los artefactos cualquier propuesta descartada que se compartió únicamente como contexto. La documentación describirá la solución elegida y sus límites, sin reabrir alternativas descartadas.
- **S9 — Calidad.** Añadir pruebas del contrato, catálogo, compilador, revisiones y compatibilidad; cerrar ejecutando formato, lint, typecheck, tests y build con pnpm. Cualquier prueba no ejecutada o fallo ambiental debe quedar explícito.
